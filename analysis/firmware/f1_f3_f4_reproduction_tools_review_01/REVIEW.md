# Source → sealed User → FWP tooling review

This is an independent read-only review of Root's current reproduction, compilation, packaging and freezing scripts. No camera, SDK, Windows session, native library, target code or network operation was used. The final corrected functional candidate and its complete pipeline are still pending; this review does not substitute for that execution.

The reproduction path really recompiles each current frozen target object from its recorded successful Zig compile, verifies each fresh byte count/hash, and compiles both Root C objects. The object map is used as the link input rather than reusing prior payload bytes. The full User is independently reviewed before sealing, receives the directory-independent semantic seal and exact loader proof, is reviewed again, and is compared in every byte with the reference sealed User. The official stock-wrapper packager then rebuilds both nested containers and both are compared in every byte with the reference files. No seal bytes or package entries are ignored.

The package inspector regenerates the complete package locally from the exact stock wrapper and the reviewed User. It checks PLAN equality, full FWR/FWP equality, both CRC checks, exactly two entries at each nesting level, the system/release/component versions, the sole LinuxApp type, and the actual embedded User bytes. The packaging scripts do not deploy or validate target boot/recovery.

The initial narrow review found that source locking/freezing handled only selected manifest keys. The actual current source manifests also declare `references`, `artifacts` and `external_exact_inputs`. A read-only coverage model using the historical `INPUTS_FINAL_01.json` found 68 such rows not covered elsewhere, including eight distinct actual compiler-record files. Root fixed this before freezing: both `build.lock()` and `freeze.manifest()` now recursively consume exact `path/bytes/sha256` rows **within the current manifest JSON**, without opening arbitrary historical diagnostic JSONs or reassigning their recorded source identities. Freeze also explicitly retains each actual object's selected COMMANDS/BUILD record, the ABI proof, unwind02 source lock and the complete reproduction receipt/object/container tree. This closes the reported source and compile-record omission.

Two small integrity recommendations were also applied. Reproduction now checks the reference User byte count/hash against its BUILD row before comparison. Freeze validates the requested archive's scope and absence before writing its source manifest. Output build/reproduction directories and package-inspection result files reject overwrite. Each compiler/subprocess result, stdout and stderr is retained locally before its success assertion. Link exceptions retain `LINK_FAILURE.json`. Failed outputs are not converted into a successful reproduction receipt. Failures after directory creation can leave inspectable partial outputs; those require a new output directory, as documented by the fresh-build flow.

The ZIP is explicitly a local **source supplement to the original workspace**, not a standalone toolchain or all licensed inputs. It retains source/header/script/JSON/document/dependency-list files with deterministic ZIP dates, ordering and permissions. Compiler executables, original firmware and library ELF files, prior binary objects and target firmware containers are excluded from the ZIP by the suffix allowlist, although their required local identities are retained in the lock manifest. The README says those exact original inputs remain required. The reviewed scripts contain no device/SDK/network upload operation and no private originals are sent anywhere.

No remaining P0/P1 was identified in the reviewed corrected scripts. The final four overlays and actual final02 complete source → sealed User → FWR/FWP run still need their own recorded results. The immutable contract's eleven actual-ELF host C mutation/readback cases are ready to be rerun on that final file. Static code, source/container reproduction and host readback remain separate from actual camera rendering, recording, persistence and recovery acceptance.
