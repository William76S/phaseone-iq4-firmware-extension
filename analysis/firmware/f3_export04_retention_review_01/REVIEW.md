# Export04 cleanup retention: offline integration review

The 26 export04 freeze members and all 27 nested export03 members match their recorded bytes and hashes. This review did not repeat the already recorded 62 normal/62 ASan/UBSan tests or execute original firmware functions.

**P1 integration requirement:** a sink returning an ordinary failure code is insufficient to retain the native full-RAW owner. Frozen `f3_native_render_02/adapter.cpp:163-165` calls `finish(Result::Sink)` for every non-F3_OK sink return. `finish` invokes cleanup, destroys planar/RGB32/generator/settings and clears `source_held` at lines65-69. Therefore an export04 `F3_UNKNOWN_HOLD` must not return through that normal sink path.

The new coordinator's C++ sink must wait for `f3_export_stream_encode_03` to return completely, then detect `saved.status == F3_UNKNOWN_HOLD`, stream state3 or session.hold and throw its own `SinkHold`. The existing renderer catch at lines166-170 sets quarantine and returns Hold without invoking cleanup; later cleanup refuses a quarantined Session at line53. Throw only at that C++ sink boundary. Never throw from the C JPEG callback or the C transaction write callback: export04's setjmp/longjmp stays entirely in C.

The owner job must remain alive after that Hold. It includes checked stream/session and ports context, native Session and embedded objects, SourceBundle/tags/input/row table, ReaderStage storage and FD, source payload, mapped arena, independent source/card/pool reservations, capture/manual ticket, and shared activity. Neither local automatic objects leaving scope, smart-pointer destruction, nor an unconditional cleanup guard may reclaim these. The executor must receive -1/UNKNOWN and retain its task/activity.

The newly available, **not yet frozen** `coordinator.cpp` closes this routing requirement in source: lines176-177 wait for the checked C exporter to return, then throw `Retain06` on Unknown/session/ledger Hold. Lines262-266 propagate renderer Hold/quarantine to the Retain06 catch and return -1 before the cleanup call at267. Job is a process-lifetime namespace object at42; native Session/ReaderStage/SourceBundle use its own placement storage at34-38. Hold keeps the reservation, actual card/capture/activity and native graph. `cleanup` also refuses `j.hold` at116. No native automatic destructor or exception-driven source cleanup occurs on this inspected path. The corresponding snapshot hash is recorded in RESULT.json; later edits require rechecking. The condition above remains an integration contract, but it is implemented in this snapshot rather than an outstanding code defect.

Export04's C codec itself preserves its own needed heap state: API and sink descriptors are copied before setjmp; the compressor/error/destination and modified cleanup status remain in heap storage; the RGB24 row is retained on fatal destroy; the unchanged automatic context pointer survives longjmp; and no partially destroyed context is retried. Failure reports zero JPEG bytes. `stream_export.c:172-173` preserves existing state3 or converts CLEANUP_ERROR into transaction Hold; abort is inactive after Hold. The retained sink descriptor contains an external `sink.context` pointer, so its process-lifetime validity still depends on the owner job above. An atomic retained list is not an independent retention mechanism for those external native resources.

**P2 freeze boundary:** export04's manifest pins the old export03 manifest but `freeze.py:10-14` verifies only immediate file rows. It omits direct rows for `stream_rgb32.h`, `bounded_jpeg.h`, official `jconfig.h`/`jmorecfg.h`/`jpeglib.h`, stream02 `stream.h`/`sha256.h`, and transaction01 `transaction.h`; its host comparison also consumes `stream_rgb32.c`. Running only export04 `--verify` does not detect a changed dependency whose old manifest itself was left unchanged. No frozen file was edited.

No additional C longjmp owner defect was found within the narrow codec path. Full RAW rendering, target unwind execution and camera acceptance remain separate from this source/host review.
