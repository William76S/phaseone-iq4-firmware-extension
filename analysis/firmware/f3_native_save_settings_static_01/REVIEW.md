## The new-image pending trigger depends on the XQD-completion flag

`495b2c..495b44` constructs IFM+778 event named `ImageStoredOnXQD`; its inner event is +780. `495c88` initializes IFM+fb5=false. Original JpegStorage worker `8e0b18` subscribes to that event, SD JpegMode inner event, SD availability and a retry timer. Nonzero JpegMode sets fb5=true via `8e2628`. NewImages does only that; AllImages additionally counts **already flagged** pending nodes, without seeding all-image pending flags in this complete worker body.

`496784(IFM,index,flagsU8)` records file-presence flags then branches on the incoming value. At `49681c..496820`, **only flags2** enters `496854`; flag4 exits through `49684c→4968e8`. The flags2 branch optionally adds Backup pending0x80 when fb4 and adds JPEG pending0x100 through `496888→498994` when fb5, then emits ImageStoredOnXQD at `496898`. The pending mask is a separate U16 work flag, not the node's U8 file-presence flag. JPEG completion's own original flag is0x10 (`8e0994..998`) and does not trigger another JPEG.

The native RawStorage completion callback `8dbf58` sends this event bridge only after success and group+13f2 notification-enabled; it forwards group+13f3 via `8dc0bc→8c5d98→496784`. Thus SD success uses4 and XQD success uses2. Mode0 in `8dbbac` returns skip status1; neither that skip status nor the local SD mode0 path generates a substitute flags2 completion.

The whole RX direct-BL inventory finds the only direct `498994` caller at `496888`; direct immediate fb5 LDRB/STRB accesses are constructor495c88, read496874 and writer8e263c. This inventory does **not** exclude all indirect calls, alias-address accesses, external producers, or unexamined asynchronous paths. It supports the precise local limitation: the closed original SD JPEGOnly/new-image chain requires the XQD success notification and cannot be promoted to proven global JPEG-only or proven SD-only postcapture JPEG output.

An examined non-XQD candidate is directory-model `492a38`: table `b7e8d0` enables scanning for modes1..5. `492fd4(4)` enumerates pre-existing SD `.IIQ` names and ORs file-presence flag4; `493598(...,".JPG",1024,16)` enumerates existing JPEG files. This is catalog reconstruction after card/settings events; it is not a new completed-RAW pending producer. Manual action `50fab0→49752c` uses work flag8, not JPEG pending100.

## Capture-format state and source-lifetime integration boundary

`8dc478` selects the next queued RAW node (`8dc4a0`), saves it as manager+48 (`8dc4c0`), then iterates all selected native StorageGroups. Eligible groups receive the same node through `8dc570→43ede4(group+988,node)`. It sums selected group flags and at `8dc634→8c5cdc→496668` records expected file-presence flags; this path does not emit ImageStoredOnXQD. Per-group status1 optional/off/unavailable and status2 active policy lives in `8dbbac`, with rescheduling `8db860`.

The minimal new transaction design is to consume the project's own atomic format selection **once per newly selected node, after acquisition and before that fanout**, and hold the result in the transaction. UI leafs only change that one state. Card-selection, native required/optional/fallback policy, JPEG destination, backup behavior, and render-scale selection then use the snapshot; changing the UI while a capture is in progress must not retroactively change that capture. This is an implementation contract, not an existing native callback or an installed hook. The exact context/patch choice and the private transaction owner still require implementation.

When all raw-storage groups become nonbusy, `8dc13c` calls `8c5990` at `8dc1a4` and clears manager+48. `8c5990` calls original IFM/node/RAW cleanup helpers (`4966f4`, `8c27e0`, conditional `8c2958` via `6f072c`) and advances its original node/pool machinery. The no-active-group path also reaches conditional retirement at `8dc6a4`. Merely disabling XQD/SD/Host raw groups can therefore lose the owned full-RAW source needed for JPEG-only. It cannot be implemented by pretending an XQD write succeeded or emitting its storage event for a non-existent RAW file.

For global JPEG-only, a new private RAW stage must retain the full source through render/resize → JPEG exact write/close/sync/commit → verification/failure cleanup, without publishing a RAW file on the selected destination. RAW+JPEG must retain it until both requested output operations have resolved; RAW keeps native raw-save behavior. Native backup0x80 must not silently publish RAW in JPEG-only. The primitive reference/cleanup ABI, selected-card leases, fallback/failure semantics and complete-render memory bound are not established solely by this menu/pending review. Root's independent transaction/static/full-render work remains required. No full-size JPEG, global-format behavior, or device acceptance is claimed here.
