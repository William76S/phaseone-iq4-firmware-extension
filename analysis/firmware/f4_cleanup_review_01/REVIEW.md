The stock compressor ABI is API82, size584. Original `9a214c` checks version82, `9a218c` checks size584, and `9a21b4` supplies size584. The existing public-C function-table binding matches this layout; it avoids the private mem-destination wrapper which can replace a caller-local pointer on growth. RGB input is three components/JCS_RGB, borrowed synchronously until encode returns, with explicit stride/extent and a hard output capacity. No input pixel is modified.

The material conditional failure was in the frozen error path: `src/codec/bounded_jpeg.c` freed its context even after a fatal destroy longjmp; `f4_native_source_02/worker.c` then released the owned RGB slot and treated cleanup uncertainty as an ordinary finite encode failure. Native destroy is `9a2248 -> 9a3d28 -> mem+50`. The memory constructor stores `9a4230` at that slot (`9a5304`), which frees pools1/0 and the manager. Pool destruction includes indirect virtual backing-store close calls at `9a41d0` and `9a4200`. The finite static chain does not establish that every transitive cleanup callback is incapable of a fatal error. It does not establish this failure happened on hardware.

The new independent two-object revision retains an unknown encoder context and maps CLEANUP_ERROR to WORKER_HOLD without releasing its slot or writing/sealing a packet. Its worker refuses subsequent pumping/sealing. Existing `session.c:18,29,74,84` holds the dependency graph and prevents finish, card release and restart. The original frozen sources are unchanged. Host evidence includes actual live host-libjpeg pools retained after fatal-before-destroy, rather than an error injected after freeing pools. Eight normal and eight ASan/UBSan groups passed; both AArch64 objects rebuilt identically. This closes that error-handling gap in source and host validation. Integration and target behavior still require acceptance.

The recording branch copies original RGB24 into an owned slot while the native source is locked, unlocks before publishing the slot, and synchronously encodes only that independent RGB buffer. Display16 verifies the entire source RGB24 range is disjoint from its LCD output range before filling the LCD. No Surface is passed to the encoder and no mask composition is called by this branch. These are source/static isolation checks, not an accepted hardware claim.

The Matroska writer preserves observed completion timestamps as VFR nanoseconds relative to the first frame. They are software observation timestamps; neither them nor container rate proves sensor FPS. It checks JPEG dimensions against measured mode. Movie finalization includes checked writes, sync/close, readback, scanner/timestamp/dimension checks and no-overwrite publication under held source/card ownership. Actual camera mode, removable-card behavior and performance remain untested.

One smaller pre-existing boundary remains: worker's first local sequence is copied from `metadata.software_id` while the source admits zero; `native_mkv.c` rejects a zero local sequence. If recording starts on an actual source ID of zero, the first valid frame can fail as a finite file error. No evidence shows this camera's first ID is zero. The cleanup revision deliberately leaves sequence semantics unchanged; a later independent sequence-origin fix should preserve real ID gaps and wrap checks.
