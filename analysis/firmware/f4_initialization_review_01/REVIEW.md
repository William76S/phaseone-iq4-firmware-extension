# F4 first-Start readonly review

The reported `Hold / Mode Unavailable / Card Unavailable / Encoded 0 / Notifications 0` does not identify an initialization stage. The device version and actual current owner/queue fields were not supplied to this review. No target, SDK, device or Windows operation occurred and no frozen source was edited.

**P1 — the held menu erases the underlying evidence.** `f4_native_menu_03/menu.c:29` returns a zeroed view with only phase Hold once `activate()` receives UNKNOWN at line49. It no longer calls the actual entry/session view. In contrast, `f4_native_entry_03/entry.c:36` would retain the destination card ID in its failed view. Thus Card Unavailable and zero notifications in the held menu are manufactured empty UI fields, not observations that a card was absent or that no native frame notification occurred. Entry initialization lines47–55 also collapse allocation, SourceInit, MovieBindingInit, SessionInit and MenuConnect failures into one sticky failure without recording the first failed stage. The new separate diagnostic revision should preserve the actual failed stage/return code and any already-observed mode/card/counters while retaining Hold and every unknown owner. No guard should be bypassed to obtain a positive result.

**Actual native subscription parameters are consistent in the finite checked chain.** Original `0x70fe3c` writes queue at Observer+8 and name at +0x10. Original `0x70fed8` loads that queue and calls `0x710060(queue,event,observer)`. The original register passes event and queue into the 0x88-byte listener constructor `0x710524`, which stores queue+0x30 and constructs its embedded registration node+0x68; it then calls `0x710380(listener,observer)`, which stores observer+0x40. Original unregister `0x71015c` traverses queue+0x68's list and compares the event, queue and observer. The project's scan uses its sentinel at queue+0x78 and the same listener event+8/queue+0x30/observer+0x40 fields. Original `0x712790` acquires the global recursive mutex at `0xf553c0`. These exact original bytes are recorded and rechecked in EXACT.json. This narrow review found no mandatory argument-order or +0x40-slot rejection. The current runtime mutex kind, live list, concrete UI owner and successful subscription remain unobserved; the host fixture supplies these values explicitly.

**The first native initialization is not covered by the higher-level host fixture.** Entry03's fixture returns successful SourceInit, MovieBindingInit, SessionInit and MenuConnect directly. Session02's fixture supplies successful SourceAttach/Measure/Bind and ThreadPins, and substitutes a host pthread. Source03's fixture constructs the expected owner graph and subscription list itself. Those tests establish the implemented failure routing and state machine, not that a real camera populated those fields. A meaningful diagnostic must distinguish SourceInit's exact owner/pin/clock failure; the initial absent-triple scan; actual observer/control-event constructors; the two actual Subscribe calls and their post-scans; handoff; pthread-create wrapper return and native rc; and final page-guard connection. A failed or unreadable stage must remain Unknown/Hold rather than be reported as supported hardware.

**Native LV startup is separate from recorder initialization.** The entry initializes its own objects and the session attaches observers, measures the existing stream, and creates its own worker. Neither starts the original native LV client or changes its mode. The action measures an already-running original LV client. A simple unavailable/retained-frame measurement normally returns REJECTED rather than setting menu Hold, so lack of a running stream alone does not explain the reported sticky Hold. Diagnostics should report the actual original client/running/retained state only after the owner graph was verified; they should not silently invoke a guessed native Start or fabricate RGB dimensions.

No existing codec, mux, frame-rate, device, or Source tests were rerun. The new four static windows and seven reused windows were compared directly with the original User SHA256 `9b611efe64067685b770ba3984ae951684c5a401f73f77a03b316be374032cdb`. No root cause of this specific camera's Hold is asserted without the real stage receipt.
