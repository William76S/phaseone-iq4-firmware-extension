# Movie card sink 01

This is a real synchronous file backend for the native Matroska muxer, cross-compiled locally and not executed on the camera. `f4_movie_begin_01` adopts an already-held Card05/06 guard and creates only a generated exclusive `.iq4-video-<id>-<nonce>.part`. Worker packet calls use original observed timestamps and local completion IDs, never generated sensor sequence or nominal FPS. The worker may be an ordinary pthread because these operations use only held directory FDs, native syscall PLT aliases and the pure-memory/proc mounted-view guard. It does not register/wait/release original card power requests.

`f4_movie_finish_01` performs mux seal exactly once; do not seal externally first. It checks patch length, fsync and close, reopens the exact inode read-only, computes incremental whole-file SHA256, checks actual Segment length and the full native Matroska scanner (all JPEG dimensions/syntax, timestamp records, CRCs, strict sequence/order, frame count, full EOF). It compares actual readback first/last timestamps and completion sequence to the muxer's own actual packet receipts. Then it closes the reader, publishes using non-replacing renameat2 and syncs/rechecks the directory/final inode. No RAW/source file is deleted or changed. A existing final filename refuses publication while preserving the `.part`.

The caller must first stop new producer admission and complete all queued/current source-copy/encoder tasks and the callback fence. A persistent single worker may enter finalize serially; this is a task fence, not a claimed OS join. When shutting down a thread, the real thread join is separately required. After normal finish or known abort reports files_closed, the worker can close held directory FDs using Card05/06 close_dirs; the actual original UI task releases native card requests last, after all source/pool/page owners are confirmed detached. The movie sink never releases those owners itself.

Known encoder/mux/full-card failure uses `f4_movie_abort_01` to close descriptors once and preserve the original partial file. It does not repair, remove, retry or publish that file. Any close uncertainty, EIO/ENXIO/EBADF/ENODEV/ESTALE, changed mounted view or uncertain publication latches HOLD and retains remaining FDs/card owners. Subsequent finish/abort/packet calls perform no I/O. No automatic recovery, cancellation or kill occurs. A mounted-view guard is not physical hotplug immunity; the actual device has not been observed.

The Linux factory uses exact original `syscall`/`errno_location` PLT aliases already bound in Card05. Patch is AArch64 SYS_pwrite64=68; all other filesystem calls use frozen FS04 native Linux operations, including renameat2(RENAME_NOREPLACE). ENOSYS/unsupported publication preserves `.part`; it does not fall back to overwriting rename. Host checks use real Mac local files and an explicitly different atomic linkat/unlinkat non-replacement implementation; this does not prove camera renameat2 support.

`python3 tools/firmware/movie_card_01/build.py` runs 13 isolated normal and 13 ASan/UBSan real-file cases and cross-compiles two AArch64 ET_REL objects. Cases cover successful full readback/publication, exclusive collision, short write, mount change, failed patch, write-close uncertainty, existing final collision, post-publication directory-sync failure, corrupt Segment length, corrupt frame CRC, read-close uncertainty, write EIO and read EIO. Original card objects/mounts are labeled fixtures and no vendor function, target ELF, SDK or device is executed.
